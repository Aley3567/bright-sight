# Bright Sight V2 协作决策包

> 状态：进行中。这是独立于当前实现阶段（RPC 化、确认气泡）的另一轮协作任务，对应
> [`agent-v2-design.md`](agent-v2-design.md) §14 决策树里的语音识别、跨平台交互、自进化和风险授权工作。
> 自进化的核心结构已回填主设计 §10；A、B、D 以及记忆的验证门槛和具体保留期限仍未裁决。

本文交给协作者及其 Codex 使用。目标是研究和裁决尚未确定的产品、技术问题；本轮不改代码。每个结论必须写明依据、代价和对主设计的影响，不能只给供应商列表或泛泛建议。

主设计见 [`agent-v2-design.md`](agent-v2-design.md)。

## 1. 已锁定内容

以下结论不在本轮重复讨论：

- 全系统只有一条运行链：输入 → Session → 动作面 → 决策 → Policy → 执行与验证 → 结果。
- 核心只有 Session Module 与 Capability Runtime 两个 Module。
- Script、Browser、Accessibility 是 Capability Runtime 下的三个 Adapter。
- 模型不能直接生成可执行代码、selector、坐标或脚本。
- 一个决定最多执行一次；执行前检查 freshness，执行后由代码验证。
- macOS 第一版采用右 Command 按住说话、松开提交。
- 中文 ASR 必须使用用户真实语料实测，不能只根据厂商宣传决定。
- 用户纠正先形成候选技能，不能直接扩大执行白名单或修改 Policy。

## 3. 工作包 A：中文语音识别

### A1：语音能否上传云端

需要确认：用户按键期间的音频是否允许发送到云端；是否存在不能上传的场景；是否必须在离线状态继续工作。

候选方向：

- 云端主路：优先中文准确率、热词和低端设备体验，承担网络、费用和隐私成本。
- 本地主路：音频不出设备，承担模型体积、性能和跨平台调优成本。
- 云端加本地降级：可用性最完整，但第一版要维护两套行为和一致性测试。

初始建议：如果允许上传，第一版只做云端主路；本地识别作为后续能力。按键说话限制采集时段，上传前有明确状态提示。

### A2：ASR 候选范围

云端候选至少比较：

- 豆包大模型流式 ASR。
- 阿里云 Qwen/Fun-ASR Realtime。
- 腾讯云实时 ASR。

本地候选至少比较：

- sherpa-onnx 加中文 streaming 模型。
- Apple Speech 作为 macOS 基线。
- Whisper 作为离线准确率基线，不默认视为流式交互方案。

官方资料：

- <https://www.volcengine.com/docs/6561/1354871?lang=zh>
- <https://help.aliyun.com/zh/model-studio/asr-model>
- <https://cloud.tencent.com/document/product/1093/40996>
- <https://k2-fsa.github.io/sherpa/onnx/index.html>
- <https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition>

### A3：怎样选出主模型

请设计一轮可以在本机执行的 bake-off，而不是引用不可比的厂商准确率。测试集覆盖普通中文命令，中英混说、应用名和项目名，人名、网址、数字和标点，两步或三步连续任务，以及停顿、自我修正和背景噪声。

至少输出五项指标：命令槽位准确率、中文字符错误率、热词召回率、松键到 final transcript 的延迟、失败率与单次成本。

需要裁决：

1. 测试集需要多少条、录几种环境才足以做第一版选择。
2. 指标如何加权；中文槽位准确率是否拥有一票否决权。
3. 是否设置第二供应商，以及什么故障才允许切换。
4. 热词从哪里生成，能否根据当前应用动态注入。

### 可直接交给 partner Codex 的任务

> 你负责 Bright Sight V2 的中文语音识别决策。只使用官方资料核对候选能力，不修改代码。先判断云端、本地或双路的适用条件，再设计一轮使用同一批真实音频的 ASR bake-off。结果必须包含候选清单、测试语料、指标计算、淘汰门槛、预计实施复杂度和明确推荐；供应商宣传数据不得当作横向准确率结论。按本文第 7 节格式回填。

## 4. 工作包 B：跨平台交互

### B1：首发平台顺序

当前仓库的执行、感知和验证都建立在 macOS AppleScript 与 Accessibility 上。Windows 会引入 UI Automation、不同权限模型和 Task Scheduler。

需要裁决：

- macOS 先跑通，再迁移 Windows。
- macOS 与 Windows 同时保持功能对齐。
- 核心跨平台，第一批执行 Adapter 只实现 macOS。

初始建议：核心类型与 Session 保持跨平台，功能先在 macOS 跑通；Windows 在 Browser Adapter 稳定后接入。

### B2：Windows 按键

候选需要实机检查系统冲突、国际键盘布局、远程桌面和长按事件：

- 右 Ctrl：初始推荐，系统占用少，没有 Caps Lock 状态。
- 右 Alt：部分布局中是 AltGr，存在输入冲突。
- Caps Lock：位置好，但有锁定状态和用户习惯冲突。
- 自定义组合键：冲突少，按住说话不如单键自然。

需要裁决默认键与改绑机制；默认键必须能被用户修改。

### B3：Windows 桌面控制

请判断 Windows UI Automation 能否提供与 macOS AX 对齐的最小操作集：启动应用、定位当前窗口、替换文本、点击常见控件、读取值和状态。重点研究元素 identity、stale 检查和执行后验证，不能用坐标点击作为正常路径。

### B4：跨平台调度

macOS 候选是 LaunchAgent，Windows 候选是 Task Scheduler。请判断调度是否应由操作系统只负责唤醒，再由同一个 Session Module 执行业务；同时列出休眠、未登录、权限弹窗和升级后的行为。

### 可直接交给 partner Codex 的任务

> 你负责 Bright Sight V2 的跨平台输入与系统集成。基于 macOS 右 Command 按住说话这一既定交互，评估 Windows 默认键、UI Automation 最小能力和 Task Scheduler 接入方式。方案必须保持 Session 与 Capability Interface 不分叉，说明哪些能力首发只做 macOS、Windows 何时接入，并给出实机验证清单。不要提出坐标点击兜底。按本文第 7 节格式回填。

## 5. 工作包 C：自进化（核心结构已回填）

主设计 §10 已经锁定：第一版记忆覆盖结构化偏好、显式别名和候选多步技能；当前用户原话优先，作用域
越窄优先，同层冲突追问；低风险偏好由用户点击“始终如此”后启用，别名和技能展示范围、effect 与验证
方案后启用；原始纠正文本默认不保存；记忆不能绕过 Policy 或保存临时 DOM/AX 引用。

本工作包只剩三项需要以实现证据回填：

### C1：验证门槛

为 preference、alias 和 skill 分别定义 fixture、dry-run、负例和通过条件。运行成功次数只能增加证据，
不能替代首次同意。

### C2：保留与删除

确定 journal、纠正证据、候选版本和 active 版本的默认保留期限；明确删除一次 Run、遗忘一条记忆、清空
全部个人数据各自影响哪些引用和派生数据。

### C3：Workspace 解释界面

定义用户在启用前能看到的来源 Run、结构化内容、作用域、effect、验证结果与版本差异，并验证暂停、拒绝、
回滚和遗忘不会被后续候选静默逆转。

### 可直接交给 partner Codex 的任务

> 你负责补齐 Bright Sight V2 自进化机制的验证与保留细节。不要重新设计主设计 §10 已锁定的学习对象、
> 作用域和首次同意规则。请为 preference、alias、skill 给出可执行的验证门槛、保留与级联删除语义，
> 再设计 Workspace 的解释和版本操作验收；用默认浏览器偏好、“我的 GitHub”别名、一次更短的网页路径、
> 一个失败后应停用的定时技能验证。按本文第 7 节格式回填。

## 6. 工作包 D：风险授权与定时任务

### D1：动作怎样确认

当前建议按 effect 分类：`read` 自动执行，`navigate` 限于受控窗口，`draft` 只填写，`submit` 首次确认，`change` 按可逆性确认，`destroy` 始终确认。

需要裁决：确认是针对单次动作、当前会话、目标对象，还是固定版本技能。还要定义目标变化、账号变化或应用升级后，旧确认何时失效。

### D2：定时任务怎样授权

schedule 只绑定固定版本技能和输入。请确定哪些 effect 可以预授权，哪些必须等用户在线确认；无人值守期间遇到登录、验证码、付款、发送和系统权限弹窗时如何停止。

### D3：失败与恢复

请设计统一结果：成功、可重试失败、stale、effect unknown、需要用户处理。重点说明网络错误、执行后断线和验证失败能否自动重试。涉及副作用且结果不确定时，默认答案应是停止。

### 可直接交给 partner Codex 的任务

> 你负责 Bright Sight V2 的风险授权与定时任务。沿用 effect 分类，设计单次确认、会话确认、固定技能预授权的适用范围和失效条件；再定义定时任务允许的动作、失败通知、重试和 effect-unknown 处置。方案要覆盖发消息、修改系统设置、删除文件、填写但不提交表单四个场景。按本文第 7 节格式回填。

## 7. 统一回填格式

每个工作包返回一份 Markdown，按以下结构写：

```md
# 工作包名称

## 结论
用一句话写出最终推荐及其适用前提。

## 已确认事实
- 事实及一手来源链接。

## 决策
| ID | 选择 | 理由 | 放弃的方向及原因 |
|---|---|---|---|

## 对主设计的影响
- 需要修改的 Module、Interface、状态或数据结构。

## 验证办法
- 可以实际执行的测试、样本、指标和通过门槛。

## 未决风险
- 仍需用户判断或需要实机验证的内容。
```

禁止把“建议进一步测试”“视情况而定”当作结论。没有证据的判断标注 `[推测]`；需要用户偏好才能决定的内容写成一个具体问题。

## 8. 合并顺序

四份结果回收后按以下顺序并入主设计：

1. 先合并 A 与 B，确定输入层和首发平台。
2. 再合并 C，确定哪些纠正可以形成技能。
3. 最后用 D 统一普通执行、技能执行和定时执行的授权规则。
4. 冲突结论不折中拼接；回到对应决策 ID，让用户裁决。

合并完成后删除本文中的重复背景，只把最终决定、理由和验证门槛留在主设计中。
